# AGENTS.md

## 1. 프로젝트 개요

- 프로젝트명: 기억서랍
- 서비스 형태: 모바일 웹
- 서비스 설명: 영수증·티켓·손편지를 촬영해 종이에 남은 정보와 사용자의 감정을 앞·뒷면 추억 카드와 연도별 서랍에 보관하는 AI 감성 기록 서비스
- 핵심 가치: 가격과 날짜만 저장하는 것이 아니라 누구와 함께했고 무엇을 느꼈는지 사용자가 직접 기록한다.
- AI의 역할: 기억을 새로 만들지 않고 문서 인식, 정보 추출, 문서 유형 후보 제안과 사용자의 회상 정리만 보조한다.
- 해커톤 예선 제출 마감: 2026년 8월 3일 18:00
- 새로운 부가 기능보다 핵심 사용자 흐름의 정상 동작, 데이터 안전성과 안정성을 우선한다.

## 2. 기준 문서와 우선순위

작업을 시작하기 전에 다음 문서를 모두 확인한다.

- `AGENTS.md`: 에이전트의 작업 범위, 코드·보안·Git 규칙
- `README.md`: 서비스 목적, MVP 기능 범위, 사용자 경험
- `docs/API_SPEC.md`: 엔드포인트, 요청·응답 필드, enum, 상태 코드, AI 처리 순서
- 실제 소스 코드와 설정 파일: 현재 구현 상태와 실행 환경

우선순위는 다음과 같다.

1. API 계약과 AI 내부 처리 순서는 `docs/API_SPEC.md`를 기준으로 한다.
2. 서비스 목적과 MVP 포함·제외 범위는 `README.md`를 기준으로 한다.
3. 개발 환경은 이 문서에 명시된 확정 버전을 따른다.
4. 코드가 문서와 다르더라도 코드를 임의로 정답으로 간주하지 않는다.

규칙:

- 문서 간 충돌을 발견하면 임의로 해석하거나 새 정책을 만들지 말고 충돌한 파일과 항목을 먼저 보고한다.
- API 엔드포인트, 필드명, 자료형, enum, 상태 코드와 오류 코드를 임의로 변경하지 않는다.
- API 계약 또는 핵심 사용자 흐름을 변경해야 한다면 구현 코드, 테스트와 관련 문서를 같은 작업에서 함께 수정한다.
- `docs/API_SPEC.md`의 TODO 항목은 팀이 확정하기 전까지 임의로 결정하지 않는다.
- 관련 문서를 읽지 않은 상태에서 기능 구현을 시작하지 않는다.

## 3. 확정 개발 환경

### 3.1 Frontend

- React
- JavaScript
- Vite
- Node.js 24 LTS
- npm
- 기본 개발 주소: `http://localhost:5173`
- API 기본 경로: `/api`
- 모바일 화면 우선 구현

규칙:

- TypeScript로 전환하지 않는다.
- Yarn 또는 pnpm으로 패키지 관리자를 바꾸지 않는다.
- `package-lock.json`을 생성하고 Git에 포함한다.
- React, Vite와 npm의 버전을 임의로 대규모 업그레이드하지 않는다.
- `VITE_API_BASE_URL`의 기본값은 `/api`로 사용한다.
- 개발 환경에서는 `/api` 요청을 `http://localhost:8080`으로 전달하는 Vite 프록시를 사용한다.
- 실제 API 키나 비밀번호를 `VITE_*` 환경 변수에 넣지 않는다.
- Upstage API는 프론트엔드에서 직접 호출하지 않는다.

- Spring Boot 3.5.16
- Gradle Wrapper
- Gradle Groovy DSL
- MySQL 8.4
- 기본 서버 포트: `8080`
- 공개 API Base URL: `/api`

기본 의존성:

- Spring Web
- Spring Security
- Spring Data JPA
- Validation
- MySQL Driver
- H2 Database는 테스트 전용으로만 사용

규칙:

- 시스템에 설치된 전역 Gradle이 아니라 저장소의 Gradle Wrapper를 사용한다.
- `gradlew`, `gradlew.bat`, `gradle/wrapper/`를 Git에 포함한다.
- Java 버전을 17, 22 또는 다른 버전으로 임의 변경하지 않는다.
- 실제 로컬·운영 DB는 MySQL 8.4를 기준으로 한다.
- H2를 운영 또는 일반 로컬 실행용 DB로 사용하지 않는다.
- Spring Boot, Gradle 또는 데이터베이스를 임의로 다른 기술로 변경하지 않는다.
- 새로운 대형 의존성을 추가하기 전에 기존 의존성으로 해결할 수 없는 이유와 영향을 설명한다.
- 초기 환경 구성 단계에서는 Lombok, Flyway, WebFlux, JWT 라이브러리, AWS SDK와 OpenCV를 임의로 추가하지 않는다.
- 해당 기능을 실제로 구현하는 작업에서 필요성이 확인된 경우에만 의존성 추가를 검토한다.

- 실제 `.env`, `.env.local`, 비밀번호, 토큰과 API 키는 Git에 포함하지 않는다.
- 예시 환경 파일에는 변수명과 가짜 값만 작성한다.
- Upstage API 키를 프론트엔드 파일이나 브라우저 번들에 포함하지 않는다.

## 5. 임시 기록과 사용자 확인 순서

이미지는 `/memory-drafts/analyze`에서 한 번 업로드하고, 백엔드는 이미지와 분석 중간 결과를 `draftId`에 연결해 임시 보관한다.

임시 기록 상태는 다음 값을 사용한다.

- `TYPE_PENDING`: AI가 제안한 문서 유형을 사용자가 확인하기 전
- `FRONT_PENDING`: 문서 유형은 확정됐지만 추출 결과를 확인하기 전
- `FRONT_CONFIRMED`: 사용자가 수정된 추출값을 확인해 앞면이 확정됨
- `SAVED`: 최종 카드가 저장됨

상태 전이는 다음 순서를 따른다.

```text
TYPE_PENDING
→ FRONT_PENDING
→ FRONT_CONFIRMED
→ SAVED
```

규칙:

- 현재 상태에서 허용되지 않는 API 호출은 `docs/API_SPEC.md`의 `409` 오류로 처리한다.
- 사용자가 문서 유형을 확정하기 전에 유형별 정보를 최종값으로 저장하지 않는다.
- 사용자가 추출 결과를 확인하기 전에 카드 앞면을 확정하지 않는다.
- 사용자는 최종 저장 전까지 앞면 확인 API를 다시 호출해 값을 수정할 수 있다.
- 최종 카드에는 AI 최초 후보가 아니라 사용자가 확인·수정한 최종값만 저장한다.
- 외부 API 호출과 응답 검증이 성공한 뒤에만 다음 상태로 변경한다.
- `SAVED` 상태의 `draftId`로 카드를 중복 생성하지 않는다.
- 저장 후에는 소유한 카드의 날짜와 앞·뒷면 텍스트 정보를 수정하거나 카드를 삭제할 수 있다.
- 카드 수정 시 문서 유형·티켓 작성 방식·원본 이미지·추가 사진은 변경하지 않고 기존 값을 유지한다.
- 영수증 카드 수정에는 `purchaseItems`를 포함하며, 기존 클라이언트가 필드를 생략하면 저장된 품목을 유지한다.

## 6. 반드시 지켜야 하는 서비스 규칙

- AI가 추출하거나 생성한 사용자 확인 대상 결과는 확정값이 아니라 후보값이다.
- 문서 유형과 티켓 세부 유형은 사용자가 확인하거나 직접 변경할 수 있어야 한다.
- 추출 결과와 AI 생성 제목은 사용자가 수정한 뒤 확정할 수 있어야 한다.
- 찾지 못하거나 확신할 수 없는 값은 임의로 채우지 않고 `null`로 반환한다.
- 입력하지 않은 문자열은 빈 문자열 `""` 대신 `null`을 사용한다.
- 날짜를 찾지 못했을 때 오늘 날짜를 자동으로 입력하지 않는다.
- 동행인·날씨·기분은 AI가 추측하지 않고 사용자가 직접 선택하거나 입력한다.
- 영수증·티켓·손편지의 카드 배경은 모두 흰색으로 통일한다.
- 영수증·티켓 앞면에는 사용자가 확인한 추출값만 표시하고, 분석에 사용한 원본 이미지는 표시하지 않는다.
- 손편지 앞면에도 업로드 원본 또는 배경 제거 이미지를 표시하지 않고 사용자가 확인한 `ocrText`만 표시한다.
- 카드 배경색을 사용자가 선택하거나 변경하는 기능을 만들지 않는다.
- 영수증·티켓은 사용자가 확인한 값으로, 손편지는 사용자가 확인한 OCR 본문으로 최종 카드를 만든다.
- 추출 결과 확인 화면에는 원본 이미지를 함께 표시하지 않고 추출 결과만 표시한다.
- 선택 필드가 `null`이면 최종 카드에서 값뿐 아니라 항목명도 숨긴다.
- 사용자가 최종 저장하기 전에는 완성된 추억 카드로 확정하지 않는다.
- API에 수정 필드가 없는 `frontImageMode` 등을 임의로 사용자 편집 대상으로 만들지 않는다.

## 7. 기록 종류별 규칙

### 7.1 영수증

- 자동 추출 대상은 `memoryDate`, `storeName`, `purchaseItems`이다.
- `memoryDate`, `storeName`은 카드 앞면 확정 시 필수이며 `purchaseItems`는 빈 배열을 허용한다.
- 값이 `null`이면 사용자가 직접 입력할 수 있어야 한다.
- `purchaseItems`에는 실제 구매·주문한 메뉴·상품만 남기고 합계·부가세·할인·결제·사업자·광고 행과 카페·음식점의 단순 옵션을 제외한다.
- 구매 품목은 후보로 제공하며 사용자가 이름·수량을 수정하고 추가·삭제·선택한 최종 항목만 카드 앞면에 저장한다.
- 영수증에 없는 가격, 구매 품목이나 당시 상황을 추측하지 않는다.
- 뒷면에는 사용자가 동행인·날씨·기분과 자유 기록 또는 추가 사진을 입력한다.
- `diaryText`와 `backPhotos` 중 하나 이상을 입력한다.

### 7.2 티켓

- 자동 추출 대상은 `memoryDate`, `eventName`, `venue`, `seat`이다.
- `memoryDate`, `eventName`, `venue`는 카드 앞면 확정 시 필수다.
- `seat`는 선택 필드이며 `null`일 수 있다.
- 티켓도 영수증·손편지와 동일하게 흰색 카드 배경을 사용한다.
- 티켓 이미지에서 카드 배경색을 추출·저장·반환하지 않는다.
- 티켓 작성 방식은 `DIRECT`와 `AI_RECALL`만 사용한다.
- `DIRECT`에서는 세부 유형을 묻거나 저장하지 않고 사용자가 제목과 추억을 직접 입력한다.
- `AI_RECALL`을 선택한 경우에만 티켓 세부 유형 후보를 생성한다.
- 티켓 세부 유형 enum은 다음 값만 사용한다.
  - `CONCERT_PERFORMANCE`: 콘서트·공연
  - `MOVIE`: 영화
  - `EXHIBITION`: 전시
- 세부 유형은 자동 확정하지 않고 사용자가 확인하거나 변경한다.
- 직접 기록을 선택한 사용자를 AI 질문 흐름으로 강제하지 않는다.

### 7.3 손편지

- 전체 본문은 처음 저장한 Document Parse 결과에서 가져와 `ocrText`로 제공한다.
- 손편지 정보 추출을 위해 Information Extract를 호출하지 않는다.
- 손편지 날짜는 자동 추출하지 않고 `memoryDate: null`로 반환한다.
- 카드 앞면 확정 전에 사용자가 실제 추억 날짜를 직접 입력한다.
- 인식하지 못한 글자를 임의로 보완하지 않는다.
- 사용자는 인식된 `ocrText`를 확인하고 잘못된 부분을 수정할 수 있다.
- 업로드 원본은 분석과 내부 보관에만 사용하고 연도별 목록과 카드 상세 앞면에는 표시하지 않는다.
- 뒷면의 `diaryText`와 `backPhotos` 중 하나 이상을 입력한다.

## 8. Upstage API 사용 규칙

Upstage API는 Spring Boot 백엔드에서만 호출한다. 프론트엔드 코드, 브라우저 네트워크 응답과 빌드 결과물에 Upstage API 키나 원본 응답을 노출하지 않는다.

전체 호출 순서는 다음과 같다.

```text
이미지 업로드
→ Document Parse 1회
→ 저장된 Document Parse 결과로 Solar 문서 유형 후보 생성
→ 사용자 문서 유형 확인
→ 영수증·티켓은 원본 이미지로 Information Extract 독립 호출
→ 손편지는 저장된 Document Parse 전체 본문 재사용
→ 사용자 추출값 확인·수정
→ 카드 앞면 확정
→ 티켓 AI 질문 선택 시 저장된 Document Parse 결과로 Solar 세부 유형 후보 생성
→ 서버 고정 질문 전체 표시
→ 사용자 답변만 근거로 Solar 제목 한 줄 생성
→ 사용자 최종 확인 후 카드 저장
```

### 8.1 Document Parse

- `/memory-drafts/analyze`에서 업로드된 문서의 전체 텍스트와 구조를 인식한다.
- 같은 임시 기록의 이미지를 Document Parse에 반복 전송하지 않는다.
- 결과를 내부 `parsedContent` 형식으로 정규화해 `draftId`에 연결한다.
- `parsedContent`는 문서 유형 판단, 손편지 본문과 티켓 세부 유형 판단에 재사용한다.
- 원본 Upstage 응답과 `parsedContent`를 프론트엔드에 그대로 반환하지 않는다.
- 유효한 본문을 얻지 못하면 `422 DOCUMENT_001`을 반환한다.

### 8.2 Information Extract

- 사용자가 문서 유형을 확정한 뒤 영수증 또는 티켓에만 호출한다.
- 입력은 Document Parse 결과가 아니라 `draftId`에 연결된 원본 문서 이미지다.
- Document Parse와 Information Extract는 독립된 API로 구현한다.
- 영수증 스키마는 `memoryDate`, `storeName`, `purchaseItems`만 사용한다.
- 티켓 스키마는 `memoryDate`, `eventName`, `venue`, `seat`만 사용한다.
- 정의하지 않은 추출 필드는 저장하거나 프론트엔드에 반환하지 않는다.
- 날짜를 `YYYY-MM-DD`로 정규화할 수 없거나 값이 불확실하면 `null`로 반환한다.
- 카드 배경색을 추출하는 용도로 사용하지 않는다.
- 손편지에는 Information Extract를 호출하지 않는다.

### 8.3 Solar

Solar는 다음 세 작업에서만 호출한다.

1. Document Parse 결과를 바탕으로 최초 문서 유형 후보 생성
2. 사용자가 티켓에서 `AI_RECALL`을 선택한 경우 세부 유형 후보 생성
3. 서버 고정 질문에 대한 사용자의 답변만 바탕으로 제목 한 줄 생성

문서 유형 결과는 다음 값만 허용한다.

```text
RECEIPT | TICKET | LETTER | UNKNOWN
```

티켓 세부 유형 결과는 다음 값만 허용한다.

```text
CONCERT_PERFORMANCE | MOVIE | EXHIBITION | UNKNOWN
```

규칙:

- 가능하면 Structured Outputs를 사용하고 백엔드에서도 허용된 enum과 결과 형식을 다시 검증한다.
- `UNKNOWN`은 외부 API 오류가 아니다.
- 문서 유형 `UNKNOWN`은 `suggestedDocumentType: null`과 `requiresManualSelection: true`로 변환한다.
- 티켓 세부 유형 `UNKNOWN`은 `suggestedTicketSubtype: null`과 `requiresManualSelection: true`로 변환한다.
- Solar는 회상 질문을 생성하지 않는다.
- 질문은 서버의 고정 질문 은행에서만 반환한다.
- 확정된 티켓 유형의 질문 세 개를 정해진 순서대로 모두 표시한다.
- 제목 생성에는 비어 있지 않은 사용자 답변만 사실 근거로 전달한다.
- 제목은 답변을 나열하거나 그대로 이어 붙이지 않고, 답변들이 함께 나타내는 핵심 장면이나 의미를 한 줄로 압축한다.
- 제목은 공백 포함 8~24자를 권장하되, 팀이 최대 길이를 확정하기 전까지 API 강제 제한으로 사용하지 않는다.
- 날짜·장소·앞면 정보·동행인·날씨·기분을 제목 생성을 위한 추가 사실로 전달하지 않는다.
- 사용자 답변에 없는 사실·인물·감정을 추가하지 않는다.
- 답변의 의미를 바꾸거나 감정을 과장하지 않는다.
- Solar는 별도의 `한 줄 추억`, `memoryTextCandidate` 또는 질문을 생성하지 않는다.
- 제목 생성 결과는 `titleCandidate` 한 줄만 반환한다.
- 생성된 제목은 사용자가 수정하고 최종 확정해야 한다.

### 8.4 티켓 고정 질문과 답변

- 질문은 `docs/API_SPEC.md`의 서버 질문 은행을 그대로 사용한다.
- 질문 문구와 `questionId`를 프론트엔드가 임의로 생성하거나 변경하지 않는다.
- 프론트엔드는 세 질문의 서로 다른 `questionId`를 각각 한 번씩 전송한다.
- 답하지 않은 질문은 `answer: null`로 전송한다.
- 하나 이상의 답변은 비어 있지 않아야 한다.
- 프론트엔드는 질문 문구를 제목 생성 요청에 다시 보내지 않는다.
- 백엔드는 `questionId`를 서버 질문 은행과 대조한 뒤 Solar 입력과 카드 저장에 사용한다.

## 9. AI 결과와 외부 API 오류 처리

AI가 판단하지 못한 상태와 외부 API 호출 실패를 구분한다.

### 9.1 정상적인 미확정 결과

- Solar 문서 유형 결과가 `UNKNOWN`이면 `200 OK`로 응답하고 사용자가 문서 유형을 직접 선택하게 한다.
- Solar 티켓 세부 유형 결과가 `UNKNOWN`이면 `200 OK`로 응답하고 사용자가 세부 유형을 직접 선택하게 한다.
- Information Extract 필드가 불확실하면 해당 필드를 `null`로 반환하고 사용자가 직접 입력하게 한다.
- 이 상황을 `503` 오류로 처리하지 않는다.

### 9.2 외부 API 오류

- Document Parse 또는 Information Extract 호출 실패는 `503 AI_001`로 변환한다.
- Solar의 문서 유형·티켓 세부 유형·제목 생성 호출 실패는 `503 AI_002`로 변환한다.
- 외부 API 실패를 `UNKNOWN`이나 `null`의 정상 응답으로 위장하지 않는다.
- 실패 시 이미 저장된 사용자 입력과 `draftId`를 유지한다.
- 외부 호출과 응답 검증이 모두 성공한 뒤에만 임시 기록 상태를 변경한다.
- 문서 분석·정보 추출·세부 유형 호출 실패 시 사용자가 같은 단계를 재시도할 수 있게 한다.
- Solar 제목 생성에 실패하면 사용자의 답변을 보존하고 제목을 직접 입력해 계속 저장할 수 있게 한다.
- 오류 코드와 HTTP 상태는 `docs/API_SPEC.md`를 그대로 따른다.

## 10. 프론트엔드와 백엔드 경계

### 10.1 프론트엔드

- 모바일 화면을 우선으로 구현한다.
- 카메라 촬영과 앨범 파일 선택을 모두 지원한다.
- 업로드 전에 이미지 미리보기와 필요한 방향·크기 보정을 제공한다.
- 문서가 흐리거나 잘렸다면 다시 촬영하거나 다른 이미지를 선택할 수 있게 한다.
- AI 분석 중에는 로딩 상태를 표시한다.
- 문서 유형 후보는 enum에 맞는 문서 유형 카드로 표시한다.
- 추출 결과 확인 화면에는 원본 이미지를 함께 표시하지 않는다.
- `null` 추출값은 빈 입력칸으로 제공한다.
- 자동 추출값과 AI 생성 제목을 사용자가 직접 수정할 수 있게 한다.
- 영수증 구매 품목 후보를 사용자가 수정·추가·삭제·선택하고 최종 선택 항목만 전송할 수 있게 한다.
- 영수증·티켓·손편지 카드의 배경을 모두 흰색으로 렌더링한다.
- 영수증·티켓·손편지 카드에는 업로드한 원본 이미지를 렌더링하지 않는다.
- 원본 이미지에서 카드 배경색을 추출하거나 사용자가 배경색을 선택하는 UI를 만들지 않는다.
- `seat` 등 선택값이 `null`이면 최종 카드에서 항목명도 숨긴다.
- 티켓 직접 기록에서는 세부 유형 API를 호출하지 않는다.
- 티켓 AI 회상에서는 확정된 유형의 고정 질문을 모두 표시한다.
- AI 제목 후보는 수정 가능한 입력칸으로 표시한다.
- Upstage API를 직접 호출하지 않는다.
- 사용자에게 복구 가능한 오류 안내와 재시도 경로를 제공한다.
- 카드 프레임 아래의 경과일은 `memoryDate`와 사용자 기기 날짜로 계산하고 1분마다 날짜 변경을 확인한다.

### 10.2 백엔드

- 인증, 사용자별 데이터 접근, 임시 기록 상태, 이미지 저장과 Upstage API 호출을 담당한다.
- API 키와 DB 비밀정보를 환경 변수로 관리한다.
- 로그인 사용자가 자신의 임시 기록과 카드만 조회할 수 있도록 소유권을 검증한다.
- 요청 본문의 사용자 ID를 신뢰하지 않고 인증 토큰의 사용자 ID를 사용한다.
- 다른 사용자의 `draftId` 또는 `cardId` 접근은 `403`으로 처리한다.
- 외부 API의 시간 초과, 실패 응답과 잘못된 응답 형식을 검증한다.
- `draftId` 기반 분석·확인·저장 흐름을 유지한다.
- 사용자가 확인하기 전의 분석 후보를 최종 카드로 저장하지 않는다.
- 같은 `draftId`의 중복 카드 생성을 막는다.
- 카드 배경색을 계산·저장·반환하지 않는다.
- 저장된 카드의 수정·삭제에서도 소유권을 확인하고 다른 사용자의 접근을 `403`으로 처리한다.
- 카드 삭제는 DB 삭제가 확정된 뒤 연결된 원본·추가 사진을 정리한다.

## 11. API 계약 규칙

- 공개 API의 Base URL은 `/api`를 사용한다.
- 엔드포인트, 요청·응답 구조와 상태 코드는 `docs/API_SPEC.md`를 따른다.
- 프론트엔드와 협의 없이 경로, 필드명, enum 또는 자료형을 변경하지 않는다.
- API 명세에 없는 필드를 편의를 위해 임의로 추가하지 않는다.
- `RECEIPT`, `TICKET`, `LETTER` 외의 문서 유형을 추가하지 않는다.
- 티켓 세부 유형은 `CONCERT_PERFORMANCE`, `MOVIE`, `EXHIBITION`만 사용한다.
- 티켓 작성 방식은 `DIRECT`, `AI_RECALL`만 사용한다.
- 카드 배경색과 관련된 필드를 추가하지 않는다.
- 티켓을 포함한 모든 카드의 흰색 배경은 프론트엔드 표시 규칙이며 API 데이터로 주고받지 않는다.
- 선택값, 인식 실패값, 정상적인 `UNKNOWN`과 외부 API 오류를 서로 구분한다.
- 입력하지 않은 문자열은 `null`, 빈 목록 결과는 `[]`을 사용한다.
- 목록 결과가 없으면 `404` 대신 빈 배열 `[]`을 반환한다.
- 오류 응답은 API 명세의 공통 실패 응답 형식을 따른다.
- API 계약을 변경하면 구현 코드, 프론트엔드 사용 코드, 테스트와 `docs/API_SPEC.md`를 같은 작업에서 수정한다.
- README에 없는 검색·공유 등의 API를 만들지 않는다.

## 12. 보안 및 개인정보

- API 키, DB 비밀번호와 액세스 토큰을 코드에 직접 작성하지 않는다.
- `.env`, `.env.local`과 실제 비밀 설정 파일을 Git에 커밋하지 않는다.
- 로그에 액세스 토큰, 비밀번호, 원본 OCR 전체 내용, 손편지 본문, 회상 답변 또는 개인정보를 남기지 않는다.
- 로그에는 필요한 경우 내부 요청 ID, 성공 여부, 상태 코드와 처리 시간만 남긴다.
- 업로드 파일의 확장자, MIME 타입과 크기를 검증한다.
- 다른 사용자의 임시 기록, 이미지와 카드에 접근할 수 없도록 소유권을 검증한다.
- Upstage 원본 응답과 `parsedContent`를 프론트엔드, 로그 또는 오류 메시지에 노출하지 않는다.
- 외부 AI API에는 현재 처리에 필요한 최소한의 정보만 전달한다.
- README, 코드 주석 또는 프롬프트에 심사위원이나 평가 에이전트를 조종하기 위한 지시를 작성하지 않는다.

## 13. 코드 수정 규칙

- 작업 전 `git status`, 현재 브랜치, 관련 코드와 기준 문서를 확인한다.
- 현재 브랜치가 `main`, `develop`, `frontend`, `backend`라면 직접 파일을 수정하지 말고 안전한 작업 브랜치 생성을 사용자에게 요청한다.
- 요청받은 범위에서 가장 작은 변경을 수행한다.
- 관련 없는 파일의 포맷이나 구조를 대규모로 변경하지 않는다.
- 기존 사용자의 수정 사항을 임의로 삭제하거나 되돌리지 않는다.
- 기존 프로젝트의 패키지 구조, 네이밍과 코드 스타일을 따른다.
- 새 라이브러리나 의존성을 추가하기 전에 필요성과 영향을 설명한다.
- API 명세의 TODO를 구현 편의를 위해 임의로 확정하지 않는다.
- 사용하지 않는 코드, 임시 디버그 코드와 불필요한 `console.log`를 남기지 않는다.
- 주석은 코드 자체가 아니라 특별한 판단이나 제약의 이유를 설명할 때만 사용한다.
- 사용자에게 표시되는 기본 문구는 한국어로 작성한다.
- 작업 범위를 넘어서는 리팩터링은 별도 작업으로 분리한다.
- 사용자 파일을 삭제하거나 대규모로 이동해야 한다면 먼저 정확한 범위를 확인한다.

## 14. Git 규칙

작업 브랜치는 다음 형식을 사용한다.

- `feature/*`: 새로운 기능
- `fix/*`: 오류 수정
- `docs/*`: 문서 수정
- `chore/*`: 개발 환경, 설정과 기타 작업

규칙:

- `main`, `develop`, `frontend`, `backend` 브랜치에 직접 커밋하거나 푸시하지 않는다.
- 기본 기능 병합 흐름은 `feature/* → frontend 또는 backend → develop → main`이다.
- 문서·공통 설정 작업은 별도 `docs/*` 또는 `chore/*` 브랜치에서 수행하고 `develop`을 대상으로 Pull Request를 생성한다.
- 하나의 브랜치와 커밋에는 하나의 논리적인 작업만 포함한다.
- 명시적으로 요청받지 않았다면 에이전트가 임의로 커밋, 푸시, 병합 또는 PR 생성을 하지 않는다.
- 푸시 전 `git remote -v`로 대상 원격 저장소를 확인한다.
- 푸시는 팀 Fork의 `origin`에만 한다.
- 운영진 또는 원본 저장소인 `upstream`으로 푸시하지 않는다.
- `upstream`을 대상으로 Pull Request를 만들지 않는다.
- `main`을 대상으로 직접 Pull Request를 만들지 않는다.
- 다른 사용자의 커밋이나 작업을 강제로 되돌리지 않는다.
- `git reset --hard`, 강제 푸시와 같은 파괴적인 명령을 사용하지 않는다.
- 변경 파일을 확인하지 않고 무조건 `git add .` 하지 않는다.

커밋 메시지는 다음 접두어를 사용한다.

- `feat:` 새로운 기능
- `fix:` 오류 수정
- `docs:` 문서 수정
- `refactor:` 기능 변경 없는 구조 개선
- `test:` 테스트 추가 또는 수정
- `chore:` 설정과 기타 작업

## 15. 테스트 및 검증

- 저장소에 포함된 npm 스크립트와 Gradle Wrapper를 사용한다.
- 존재하지 않는 실행 명령이나 테스트 명령을 임의로 만들지 않는다.
- 작은 변경은 관련 테스트를 실행하고, PR 전에는 가능한 전체 테스트·빌드·린트를 실행한다.
- 테스트나 스크립트가 아직 없다면 임의로 성공했다고 판단하지 말고 해당 사실을 결과에 기록한다.

프론트엔드에서 관련 스크립트가 정의되어 있다면 다음을 검증한다.

```bash
npm ci
npm run lint
npm run build
```

백엔드는 현재 운영체제에 맞는 Gradle Wrapper를 사용한다.

Windows:

```powershell
.\gradlew.bat clean test
.\gradlew.bat build
```

macOS/Linux:

```bash
./gradlew clean test
./gradlew build
```

다음 흐름을 중점적으로 확인한다.

- 회원가입과 로그인 성공·실패
- 인증 토큰이 없는 요청
- 다른 사용자의 `draftId` 또는 `cardId` 접근
- 잘못된 형식, 크기 초과 또는 지원하지 않는 이미지 업로드
- Document Parse로 문서를 분석할 수 없는 경우
- Solar 문서 유형 결과가 `UNKNOWN`인 경우
- Information Extract 필드가 `null`인 경우
- 영수증 구매 품목에서 결제·세금·할인·사업자·광고 행과 단순 옵션이 제거되는지
- 영수증 구매 품목을 수정·추가·삭제·선택하고 최종 선택값만 저장·조회하는지
- 손편지 유형 확정 시 Information Extract를 호출하지 않는지
- Solar 티켓 세부 유형 결과가 `UNKNOWN`인 경우
- Upstage API 실패 또는 시간 초과
- 사용자가 AI 문서 유형 후보를 변경하는 흐름
- 사용자가 추출값을 수정하고 앞면을 다시 확인하는 흐름
- 티켓에서 `DIRECT`를 선택해 세부 유형·Solar API를 호출하지 않는 흐름
- 티켓에서 `AI_RECALL`을 선택해 고정 질문 전체를 받는 흐름
- 질문 ID 불일치·중복 또는 모든 답변이 비어 있는 경우
- Solar 제목 생성 실패 후 직접 제목을 입력하는 흐름
- Solar 제목이 여러 답변을 쉼표로 나열하지 않고 핵심 장면이나 의미로 압축되도록 요청하는지
- 좌석 등 선택 항목이 `null`일 때 항목명을 숨기는 흐름
- 영수증·티켓·손편지 카드 배경이 모두 흰색인지
- 영수증·티켓 앞면에 원본 이미지가 표시되지 않고 확정된 추출값만 표시되는지
- 색상 추출·선택 기능이나 카드 배경색 관련 API 필드가 없는지
- 같은 `draftId`로 중복 저장을 시도하는 경우
- 저장된 카드가 실제 `memoryDate`의 연도 서랍에 표시되는지
- 카드 프레임 아래 경과일의 당일·과거·미래 표시와 1분 갱신이 동작하는지
- 저장된 카드 수정 시 문서 유형·티켓 작성 방식·기존 사진이 유지되는지
- 영수증 카드 수정 시 구매 품목을 수정·추가·삭제할 수 있고, 누락된 구버전 요청은 기존 품목을 유지하는지
- 카드 수정·삭제에서 소유권 검증과 삭제 후 파일 정리가 동작하는지

## 16. 작업 완료 조건

다음을 모두 만족해야 작업이 완료된 것으로 판단한다.

- 요청받은 기능이 실제 사용자 흐름에서 동작한다.
- `README.md`의 MVP 범위와 `docs/API_SPEC.md`의 API 계약을 위반하지 않는다.
- Document Parse, Information Extract와 Solar의 역할과 호출 순서를 지킨다.
- AI 결과에 대한 사용자 확인과 수정 과정이 유지된다.
- `UNKNOWN`, `null`, `422`와 외부 API `503` 오류를 정확히 구분한다.
- 최종 카드에는 AI 최초 후보가 아니라 사용자 확정값이 저장된다.
- 세 기록 유형의 카드 배경이 모두 흰색이며 색상 추출·변경 기능이 없다.
- 관련 테스트, 빌드 또는 린트가 통과한다.
- 오류 상황에서 사용자가 재시도하거나 허용된 직접 입력 흐름을 이용할 수 있다.
- 코드, 설정과 로그에 비밀정보가 포함되지 않는다.
- API 또는 핵심 흐름이 바뀌었다면 관련 문서도 함께 갱신되었다.
- `git diff --check` 등으로 기본적인 변경 오류를 확인한다.
- 완료 보고에 다음 내용을 포함한다.
  - 생성하거나 수정한 파일
  - 구현한 내용
  - 실행한 검증 명령과 결과
  - 실패한 검증과 원인
  - 남은 문제와 사용자가 직접 해야 할 작업

## 17. 코딩 에이전트 설정과 AI 사용 기록

- Codex, Claude Code 등 코딩 에이전트를 사용했다면 해당 에이전트가 실제로 참고한 저장소 설정 파일을 Git에 포함한다.
- Codex를 사용하면 저장소의 `AGENTS.md`를 유지한다.
- Claude Code를 실제로 사용하고 프로젝트 전용 `.claude/` 설정을 만들었다면 해당 설정도 저장소에 포함한다.
- 사용하지 않은 에이전트의 빈 설정 디렉터리나 형식만 갖춘 설정 파일을 임의로 만들지 않는다.
- 에이전트 설정 파일에는 API 키, 비밀번호, 토큰과 개인정보를 넣지 않는다.
- 코딩 에이전트를 사용한 작업은 `docs/AI_USAGE.md`에 다음 항목을 기록한다.
  - 사용 모델·도구
  - 작업 목적
  - 사용한 프롬프트 요약
  - AI가 제안·수정한 내용
  - 팀원이 직접 결정·수정한 내용
  - 실행한 테스트와 결과
  - 발생한 문제와 해결
  - 관련 PR 또는 커밋
