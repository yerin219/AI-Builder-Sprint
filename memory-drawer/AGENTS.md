# AGENTS.md

## 1. 프로젝트 개요

- 프로젝트명: 기억서랍
- 서비스 형태: 모바일 웹
- 서비스 설명: 영수증·티켓·손쪽지를 촬영해 종이에 남은 정보와 사용자의 감정을 추억 카드와 연도별 서랍에 보관하는 AI 감성 기록 서비스
- 핵심 가치: 가격과 날짜만 저장하는 것이 아니라 누구와 함께했고 무엇을 느꼈는지 기록한다.
- AI의 역할: 기억을 새로 만들지 않고 문서 인식, 정보 추출, 사용자의 회상과 정리만 보조한다.
- 해커톤 예선 제출 마감: 2026년 8월 3일 18:00
- 새로운 부가 기능보다 핵심 사용자 흐름의 정상 동작과 안정성을 우선한다.

## 2. 기준 문서

작업을 시작하기 전에 다음 문서를 확인한다.

- `README.md`: 서비스 목적, 기능 범위, 사용자 흐름, AI 활용 방식
- `API.md`: 엔드포인트, 요청·응답 형식, 인증, 상태 코드
- 실제 소스 코드와 설정 파일: 현재 적용된 기술과 실행 환경

규칙:

- API 엔드포인트, 요청 필드, 응답 필드, 상태 코드는 `API.md`를 기준으로 한다.
- 서비스 기능과 제외 범위는 `README.md`를 기준으로 한다.
- 문서와 코드가 서로 다르면 임의로 판단하지 말고 충돌 내용을 먼저 보고한다.
- 확정되지 않은 프레임워크, 데이터베이스, 저장소, 실행 명령을 임의로 선택하지 않는다.
- API 계약이나 핵심 사용자 흐름을 변경해야 한다면 코드와 문서를 함께 수정한다.

## 3. 해커톤 MVP 범위

지원하는 기록은 다음 세 종류뿐이다.

- 영수증
- 티켓
- 손쪽지·편지

핵심 사용자 흐름은 다음과 같다.

1. 회원가입 또는 로그인
2. 카메라 촬영 또는 앨범 이미지 선택
3. 문서 전체 인식
4. 핵심 정보 추출 및 유형 후보 제안
5. 사용자 확인과 수정
6. 카드 앞면 완성
7. 카드 뒷면 기록
8. 선택적인 티켓 AI 회상 질문
9. 카드 최종 미리보기와 저장
10. 실제 추억 날짜를 기준으로 연도별 서랍에 표시

다음 기능은 현재 MVP 범위에서 제외한다.

- 음식 사진 인식
- 일반 풍경 사진 기록
- 영상 또는 음성 기록
- 복잡한 배경의 정교한 손글씨 누끼
- 사용자 입력에 없는 기억이나 감정 생성
- 새로운 기록 유형의 임의 추가

## 4. 반드시 지켜야 하는 서비스 규칙

- AI가 추출하거나 생성한 결과는 확정값이 아니라 후보값이다.
- 모든 인식 결과와 생성 결과는 사용자가 확인하고 수정할 수 있어야 한다.
- 사용자가 최종 저장하기 전에는 완성된 추억 카드로 확정하지 않는다.
- 찾지 못하거나 확신할 수 없는 값은 임의로 채우지 않고 `null` 또는 미입력 상태로 반환한다.
- 날짜를 찾지 못했을 때 오늘 날짜를 자동으로 입력하지 않는다.
- 날씨, 기분, 동행인은 AI가 추측하지 않고 사용자가 직접 선택하거나 입력한다.
- 영수증·티켓·손쪽지의 원본 형태와 색감을 최대한 보존한다.
- 원본 이미지와 사용자가 수정한 값을 함께 기준으로 최종 카드를 만든다.

## 5. 기록 종류별 규칙

### 영수증

- 자동 추출 대상은 날짜와 가게명이다.
- 값이 불확실하면 직접 입력할 수 있어야 한다.
- 영수증에 없는 소비 내용이나 상황을 추측하지 않는다.

### 티켓

- 자동 추출 대상은 날짜, 행사명, 장소, 좌석이다.
- 티켓 유형은 `콘서트`, `영화`, `공연·전시` 중 후보로 제안한다.
- 유형은 자동 확정하지 않고 사용자가 변경할 수 있어야 한다.
- 직접 기록하기를 선택한 사용자를 AI 질문 흐름으로 강제하지 않는다.
- AI 회상 질문을 선택한 경우에만 확인된 티켓 유형을 질문 선택에 사용한다.
- 원본 이미지의 대표 색상은 후보 색상으로 제공하며 사용자가 변경할 수 있어야 한다.

### 손쪽지·편지

- 전체 본문 OCR 결과를 제공한다.
- 배경이 단순할 때만 글씨 분리를 시도한다.
- 배경 제거 결과가 좋지 않으면 원본 이미지를 사용한다.
- 인식하지 못한 글자를 임의로 보완하지 않는다.

## 6. Upstage API 사용 규칙

### Document Parse

- 업로드된 문서의 전체 텍스트와 구조를 인식하는 데 사용한다.
- 원본 분석 결과를 곧바로 최종 카드 정보로 저장하지 않는다.

### Information Extract

- Document Parse 결과에서 카드에 필요한 필드를 구조화한다.
- 추출 근거가 없거나 불확실한 필드는 `null`로 반환한다.
- API 명세에 정의된 필드명과 자료형을 변경하지 않는다.

### Solar

- 티켓에서 사용자가 AI 회상 질문을 선택한 경우에만 호출한다.
- 문서와 사용자 답변에 없는 사실을 만들지 않는다.
- 이미 확인한 날짜와 장소를 다시 질문하지 않는다.
- 질문과 생성 문장은 짧고 구체적인 한국어로 작성한다.
- 사용자의 감정이나 답변을 과장하거나 의미를 변경하지 않는다.
- 생성 결과는 사용자가 수정한 뒤 확정할 수 있어야 한다.

## 7. 프론트엔드와 백엔드 경계

### 프론트엔드

- 모바일 화면을 우선으로 구현한다.
- 카메라 촬영과 앨범 파일 선택을 모두 지원한다.
- 이미지 미리보기, 방향·크기 보정, 업로드 상태를 제공한다.
- AI 분석 중에는 로딩 상태를 표시한다.
- 분석 실패 시 재시도, 재촬영 또는 직접 입력 방법을 제공한다.
- 자동 추출값과 AI 생성값을 사용자가 직접 수정할 수 있게 한다.
- Upstage API를 프론트엔드에서 직접 호출하지 않는다.
- API 키를 프론트엔드 코드나 빌드 결과물에 포함하지 않는다.

### 백엔드

- 인증, 사용자별 데이터 접근, 이미지 저장, AI API 호출을 담당한다.
- Upstage API 키는 환경변수 또는 안전한 서버 설정으로 관리한다.
- 로그인한 사용자가 자신의 기록만 조회·수정·삭제할 수 있게 검증한다.
- 외부 API의 시간 초과, 실패 응답, 잘못된 응답 형식을 처리한다.
- AI 분석 실패가 전체 서비스 오류로 이어지지 않도록 직접 입력 경로를 제공한다.
- API 명세에 정의된 `draftId` 기반 분석·확인·저장 흐름을 유지한다.
- 사용자가 확인하기 전의 분석 초안을 최종 카드로 저장하지 않는다.

## 8. API 계약 규칙

- 엔드포인트와 요청·응답 구조는 `API.md`를 따른다.
- 프론트엔드와 협의 없이 엔드포인트 경로와 필드명을 변경하지 않는다.
- 선택값과 인식 실패값을 구분한다.
- 불확실한 추출 결과를 빈 문자열이나 임의의 기본값으로 바꾸지 않는다.
- 오류 응답은 사용자가 재시도하거나 직접 입력할 수 있는 형태로 처리한다.
- API 계약을 변경하면 구현 코드, 테스트, `API.md`를 같은 작업에서 수정한다.

## 9. 보안 및 개인정보

- API 키, 비밀번호, 토큰을 코드에 직접 작성하지 않는다.
- `.env`와 실제 비밀 설정 파일을 Git에 커밋하지 않는다.
- 로그에 액세스 토큰, 비밀번호, 원본 OCR 전체 내용 또는 개인정보를 남기지 않는다.
- 업로드 파일의 확장자, MIME 타입, 크기를 검증한다.
- 사용자 ID를 요청값만 믿지 말고 인증 정보와 대조한다.
- 다른 사용자의 이미지와 카드에 접근할 수 없도록 소유권을 검증한다.
- README나 코드 주석에 심사위원 또는 평가 에이전트를 조종하기 위한 지시를 작성하지 않는다.

## 10. 코드 수정 규칙

- 작업 전 관련 코드와 문서를 먼저 읽는다.
- 요청받은 범위에서 가장 작은 변경을 수행한다.
- 관련 없는 파일의 포맷이나 구조를 대규모로 변경하지 않는다.
- 기존 사용자의 수정 사항을 임의로 삭제하거나 되돌리지 않는다.
- 기존 프로젝트의 패키지 구조, 네이밍, 코드 스타일을 따른다.
- 새 라이브러리나 의존성을 추가하기 전에 필요성을 설명한다.
- 사용하지 않는 코드, 임시 디버그 코드와 `console.log`를 남기지 않는다.
- 주석은 코드가 무엇을 하는지가 아니라 특별한 판단의 이유를 설명할 때만 사용한다.
- 사용자에게 표시되는 기본 문구는 한국어로 작성한다.

## 11. Git 규칙

- 작업 브랜치는 `feature/*`, `fix/*`, `docs/*` 형식을 사용한다.
- 기능 브랜치에서 통합 브랜치로 Pull Request를 생성한다.
- 기본 병합 흐름은 `feature/* → frontend 또는 backend → develop → main`이다.
- `develop`과 `main`에 직접 커밋하거나 푸시하지 않는다.
- 하나의 브랜치와 커밋에는 하나의 논리적인 작업만 포함한다.
- 명시적으로 요청받지 않았다면 에이전트가 임의로 커밋, 푸시 또는 병합하지 않는다.

커밋 메시지는 다음 접두어를 사용한다.

- `feat:` 새로운 기능
- `fix:` 오류 수정
- `docs:` 문서 수정
- `refactor:` 기능 변경 없는 구조 개선
- `test:` 테스트 추가 또는 수정
- `chore:` 설정과 기타 작업

## 12. 테스트 및 검증

- 저장소에 정의된 스크립트와 Wrapper를 사용한다.
- 존재하지 않는 실행 명령이나 테스트 명령을 임의로 만들지 않는다.
- 작은 변경은 관련 테스트를 실행하고, PR 전에는 제공된 전체 테스트·빌드·린트 명령을 실행한다.
- 테스트할 명령이 아직 없다면 해당 사실을 결과에 명확히 기록한다.
- 성공 경로뿐 아니라 다음 실패 경로도 확인한다.
  - 로그인하지 않은 요청
  - 다른 사용자의 기록 접근
  - 잘못된 이미지 업로드
  - 추출값이 `null`인 경우
  - Upstage API 실패 또는 시간 초과
  - AI 질문을 사용하지 않는 직접 기록 흐름
  - 사용자가 AI 결과를 수정하는 흐름

## 13. 작업 완료 조건

다음을 모두 만족해야 작업이 완료된 것으로 판단한다.

- 요청받은 기능이 실제 사용자 흐름에서 동작한다.
- `README.md`와 `API.md`의 계약을 위반하지 않는다.
- AI 결과에 대한 사용자 확인과 수정 과정이 유지된다.
- 관련 테스트, 빌드 또는 린트가 통과한다.
- 오류 상황에서 사용자에게 복구 방법을 제공한다.
- 코드와 로그에 비밀정보가 포함되지 않는다.
- 관련 문서가 함께 갱신되었다.
- 작업 결과에 변경 파일, 검증 명령과 결과, 남은 문제를 요약한다.
